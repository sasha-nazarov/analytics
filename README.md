# Workload Planner - Планировщик Загрузки Аналитиков

## Описание

Система автоматического планирования задач для бизнес-аналитиков с учетом приоритетов, сложности, времени выполнения и ограничений по загрузке. Скрипт рассчитывает оптимальные даты начала и завершения задач на квартал с учетом параллельной работы, этапов разработки и тестирования.

## Версия

**v23.0** - Независимые пайплайны аналитиков, улучшенная сортировка по сложности

## Основные концепции

### Этапы работы над задачей

Задача проходит через следующие стадии:

1. **WAIT** - Ожидание начала работы (задача в очереди)
2. **BA** - Бизнес-анализ (работа аналитика)
3. **DEV** - Разработка (на аутсорсе, не учитывается в пуле аналитика)
4. **TEST_Q** - В очереди на тестирование
5. **TEST** - Тестирование (работа аналитика)
6. **DONE** - Завершена

### Переходы между стадиями

```
WAIT → BA → DEV → TEST_Q → TEST → DONE
```

- **WAIT → BA**: Задача берется в работу аналитиком при наличии свободного места в пуле
- **BA → DEV**: После завершения БА этапа задача отправляется в разработку
- **DEV → TEST_Q**: После завершения разработки задача попадает в очередь на тестирование
- **TEST_Q → TEST**: Задача берется из очереди при наличии места в пуле
- **TEST → DONE**: После завершения тестирования задача завершается

## Конфигурация

### Параметры CONFIG

```javascript
WORK_HOURS_PER_DAY: 6.5      // Рабочих часов в день
BUFFER: 1.25                  // Буфер на непредвиденные работы (25%)
MAX_POOL: 5                   // Максимальный размер пула (BA + TEST)
MAX_BA: 3                     // Максимум BA задач одновременно
MAX_DEV_PARALLEL: 10          // Максимум параллельных DEV задач глобально
MAX_DAYS: 800                 // Максимальное количество дней расчетов
```

### Динамический пул задач по грейдам

```javascript
MAX_BA_BY_GRADE: {
  Senior: 4,   // Больше задач для Senior (больше опыта, может держать больше контекста)
  Middle: 3,   // Стандартное количество для Middle
  Junior: 2    // Меньше для Junior (меньше опыта, требуется больше концентрации)
}
```

**Примечание:** Скорость работы уже учтена в часах через градиентный буфер, поэтому отдельный GRADE_SPEED не используется.

### Коэффициенты сложности

```javascript
'Очень сложный': 1.6   // +60% к базовому времени
'Сложный': 1.3         // +30% к базовому времени
'Средний': 1.0         // Базовое время
'Легкий': 0.7          // -30% от базового времени
'Очень легкий': 0.4    // -60% от базового времени
```

### Обработка часов

**Важно:** Часы используются **как есть** из таблицы без дополнительных коэффициентов. Все необходимые буферы и коэффициенты уже учтены в таблице при расчете часов.

### Столбцы таблицы (COL)

```javascript
ANALYST: 2          // Столбец с именем аналитика
GRADE: 3            // Столбец с грейдом (Senior/Middle/Junior)
PRIORITY: 7         // Столбец с приоритетом
BA_H: 11            // Часы БА (K)
DEV_H: 12           // Часы разработки (L)
TEST_H: 13          // Часы тестирования (M)
START: 15           // Дата начала (результат)
END: 16             // Дата завершения (результат)
QUARTER_START: 17   // Дата начала квартала (Q2)
```

## Алгоритм работы

### Шаг 1: Инициализация

1. **Чтение даты начала квартала** из ячейки Q2
2. **Определение первой рабочей даты**: начиная с даты квартала, пропускаются выходные (суббота, воскресенье) и праздничные дни
3. **Чтение данных** из листа "Оценка Q4"
4. **Создание объектов задач** - часы используются как есть из таблицы:
   - `ba = ba` (из столбца K)
   - `dev = dev` (из столбца L)
   - `test = test` (из столбца M)

### Шаг 2: Подготовка задач

1. **Фильтрация**: Отбираются только задачи с ненулевыми часами (BA + DEV + TEST > 0)
2. **Группировка по аналитикам**: Задачи группируются по аналитикам
3. **Сортировка по приоритету и сложности**:
   - Сначала по приоритету: Максимальный (0) → Высокий (1) → Средний (2) → Низкий (3)
   - При одинаковом приоритете: сначала более сложные задачи (больше часов BA + DEV + TEST)
   - При одинаковой сложности: по порядку строк в таблице
4. **Инициализация первых задач**: Для каждого аналитика первые N задач начинаются с первой рабочей даты:
   - Senior: 4 задачи
   - Middle: 3 задачи
   - Junior: 2 задачи

### Шаг 3: Основной цикл обработки

**Важно:** Каждый аналитик имеет свой независимый пайплайн работ с собственной текущей датой (`analystCurrentDate`). Это означает, что аналитики работают параллельно и независимо друг от друга, каждый начиная с даты начала квартала.

Для каждого рабочего дня (пропускаются выходные и праздники):

#### 3.1. Обработка аналитиков (для каждого аналитика отдельно и независимо)

##### A. Работа над активными задачами (BA + TEST)

**Формула распределения времени:**
```
hoursPerTask = WORK_HOURS_PER_DAY / количество_активных_задач
```

Где:
- Распределение времени **равномерное** между всеми активными задачами
- Скорость работы уже учтена в часах через градиентный буфер при создании задачи

**Обработка BA задач:**
- Вычитается `hoursForTask` из `baRem`
- Если `baRem <= 0`:
  - `baRem = 0`
  - `stage = 'DEV'`
  - `active = false` (выходит из пула аналитика)
  - `devRem = dev` (устанавливается остаток DEV часов)

**Обработка TEST задач:**
- Вычитается `hoursForTask` из `testRem`
- Если `testRem <= 0`:
  - `testRem = 0`
  - `stage = 'DONE'`
  - `active = false`
  - `end = analystCurrentDate` (устанавливается дата завершения на основе даты аналитика)

##### B. Возврат задач из DEV

Задачи, у которых `stage === 'DEV'` и `devRem <= 0`, переходят в очередь тестирования:
- `stage = 'TEST_Q'`
- `active = false` (пока в очереди)
- `prio = 'Максимальный'` (приоритет повышается до максимального, только в коде)
- Добавляются в `testQueue` аналитика

Очередь сортируется по приоритету (все имеют максимальный, сохраняется порядок строк).

##### C. Управление пулом задач (циклическая обработка)

**Логика размера пула:**
```
maxPoolSize = activeTEST > 0 ? maxBAForAnalyst + 2 : maxBAForAnalyst
```

То есть:
- Если есть активные задачи в тестировании → пул расширяется до базовый размер грейда + 2
  - Senior: 4 + 2 = 6 задач
  - Middle: 3 + 2 = 5 задач
  - Junior: 2 + 2 = 4 задачи
- Если нет активных задач в тестировании → пул ограничен базовым размером для грейда

**Циклическая обработка** (пока есть изменения):

1. **Подсчет текущего пула:**
   ```
   activeBA = количество задач со stage='BA' и active=true
   activeTEST = количество задач со stage='TEST' и active=true
   currentPool = activeBA + activeTEST
   ```

2. **Приоритет 1: Задачи из очереди тестирования**
   - Если есть задачи в `testQueue` и `currentPool < maxPoolSize`:
     - Берется первая задача из очереди
     - `stage = 'TEST'`
     - `active = true`
     - `testRem = test`
     - Пересчитывается пул, цикл продолжается

3. **Приоритет 2: Новые BA задачи**
   - Если `activeBA < maxBAForAnalyst` и `currentPool < maxPoolSize`:
     - Берется первая задача из отсортированного списка со `stage = 'WAIT'`
     - `start = analystCurrentDate` (дата аналитика, когда освободилось место в пуле)
     - `stage = 'BA'`
     - `active = true`
     - `baRem = ba`
     - Пересчитывается пул, цикл продолжается

#### 3.2. Обработка DEV задач (отдельный пайплайн)

**Важно:** DEV команда работает в своем отдельном пайплайне с собственной датой (`devDate`), независимо от аналитиков. DEV команда работает спринтами (по дням с учетом выходных/праздников).

**Ограничение:** Максимум `MAX_DEV_PARALLEL` (10) задач одновременно:
- 5 программистов на аутсорсе
- Каждый программист может делать 2 задачи параллельно
- Итого: 5 × 2 = 10 задач максимум

**Приоритет:** DEV команда использует такой же приоритет, как у аналитиков:
- Максимальный → Высокий → Средний → Низкий
- При одинаковом приоритете: сначала более сложные задачи (больше часов)
- При одинаковой сложности: по порядку строк в таблице

**Цель:** Рассчитать срок завершения разработки, чтобы определить, когда аналитик сможет приступить к тестированию.

1. **Отбор и сортировка задач:**
   ```
   allDev = все задачи со stage='DEV' и devRem > 0
   sortedDev = сортировка allDev по приоритету (Максимальный → Высокий → Средний → Низкий)
   devWorking = первые MAX_DEV_PARALLEL (10) задач из sortedDev
   ```

2. **Распределение времени:**
   ```
   hoursPerDevTask = WORK_HOURS_PER_DAY / количество_активных_DEV_задач (до 10)
   ```
   
   Время распределяется **равномерно** между всеми активными DEV задачами (до 10 одновременно). Часы уже учтены в таблице.

3. **Обработка:**
   - Вычитается `hoursPerDevTask` из `devRem` для каждой активной задачи
   - Если `devRem <= 0`: `devRem = 0`

4. **Переход к следующему дню:**
   - DEV команда переходит к следующему рабочему дню (пропускаются выходные и праздники)
   - Если выходной/праздник: `devDate` просто сдвигается на день

**Замечание:** Задачи с `devRem = 0` будут обработаны на следующей итерации в разделе "Возврат из DEV". Если есть более 10 DEV задач, остальные будут обрабатываться после завершения текущих (выбор по приоритету).

### Шаг 4: Запись результатов

После завершения основного цикла:

1. Для каждой задачи записывается дата начала в столбец START
2. Для завершенных задач записывается дата завершения в столбец END
3. Проверяется, что дата начала не раньше FIRST_WORK_DAY

## Формулы расчетов

### Расчет времени выполнения задачи

**Исходные данные (из таблицы "Затраты по грейдам"):**
- `total` - общее время (часы БА)
- `development` - время разработки
- `testing` - время тестирования

**Часы берутся напрямую из таблицы:**
```javascript
ba = значение_из_столбца_K
dev = значение_из_столбца_L
test = значение_из_столбца_M
```

**Важно:** Все буферы, коэффициенты сложности и грейдов уже учтены при расчете часов в таблице. Скрипт использует готовые значения без дополнительных преобразований.

### Распределение времени в день

Для N активных задач в пуле:

```
hoursPerTask = WORK_HOURS_PER_DAY / N
```

**Пример:**
- 3 активные задачи в пуле

```
hoursPerTask = 6.5 / 3 = 2.17 часа на задачу
```

Все задачи получают **равномерное** количество времени. Скорость работы уже учтена в часах из таблицы.

### Расчет дат

**Дата начала задачи:**
- Первые N задач каждого аналитика (в зависимости от грейда): `FIRST_WORK_DAY`
  - Senior: первые 4 задачи
  - Middle: первые 3 задачи
  - Junior: первые 2 задачи
- Остальные задачи: первая доступная дата после освобождения места в пуле

**Дата завершения:**
- Устанавливается в день, когда `testRem` становится ≤ 0

## Особенности логики

### 1. Приоритеты и сортировка

- **Исходный приоритет** берется из таблицы и нормализуется (убираются пробелы, проверяется корректность)
- **При переходе в тестирование** приоритет автоматически становится "Максимальным" (только в коде, в таблице не меняется)
- **Порядок сортировки**:
  1. По приоритету: Максимальный → Высокий → Средний → Низкий
  2. При одинаковом приоритете: сначала более сложные задачи (больше суммарных часов BA + DEV + TEST)
  3. При одинаковой сложности: по порядку строк в таблице

### 2. Динамический размер пула

- **Базовый размер зависит от грейда:**
  - Senior: максимум 4 BA задачи
  - Middle: максимум 3 BA задачи
  - Junior: максимум 2 BA задачи
- **Расширенный размер**: базовый размер грейда + 2 задачи (BA + TEST), если есть активные задачи в тестировании
  - Senior: 4 + 2 = 6 задач
  - Middle: 3 + 2 = 5 задач
  - Junior: 2 + 2 = 4 задачи
- При завершении всех задач тестирования пул автоматически сжимается обратно до базового размера для грейда

### 3. Обработка выходных и праздников

- Автоматически пропускаются субботы, воскресенья
- Пропускаются праздничные дни из списка RUSSIAN_HOLIDAYS
- Рабочие часы не начисляются в выходные дни

### 4. Параллельная разработка (отдельный пайплайн DEV команды)

- **DEV команда работает в своем отдельном пайплайне** с собственной датой (`devDate`)
- DEV команда работает спринтами (по дням с учетом выходных/праздников), независимо от аналитиков
- **Ограничение**: максимум 10 DEV задач одновременно:
  - 5 программистов на аутсорсе
  - Каждый программист может делать 2 задачи параллельно
  - Итого: 5 × 2 = 10 задач максимум
- **Приоритет**: DEV команда использует такой же приоритет, как у аналитиков (Максимальный → Высокий → Средний → Низкий)
- При одинаковом приоритете: сначала более сложные задачи (больше часов)
- Время распределяется **равномерно** между всеми активными DEV задачами (до 10 одновременно)
- Цель: рассчитать срок завершения разработки для определения, когда аналитик сможет приступить к тестированию
- Если есть более 10 DEV задач, остальные обрабатываются после завершения текущих (выбор по приоритету)

### 5. Независимые пайплайны

- **Аналитики**: каждый аналитик работает в своем независимом пайплайне с собственной датой (`analystDates[analyst]`)
- **DEV команда**: работает в своем отдельном пайплайне с собственной датой (`devDate`)
- Все пайплайны начинаются с `FIRST_WORK_DAY` и работают независимо друг от друга
- Глобальный цикл продолжается, пока хотя бы один пайплайн активен (есть незавершенные задачи)

**Детали для аналитиков:**
- Каждый аналитик начинает работу с `FIRST_WORK_DAY` независимо от других
- Каждый аналитик работает в своем темпе
- Даты начала новых задач для каждого аналитика определяются на основе его собственной текущей даты
- Аналитики не пересекаются друг с другом по времени работы

**Детали для DEV команды:**
- DEV команда работает в своем пайплайне с собственной датой (`devDate`)
- DEV команда работает спринтами (по дням с учетом выходных/праздников)
- Задачи обрабатываются по приоритету (как у аналитиков)
- Максимум 10 задач одновременно (5 программистов × 2 задачи)

### 6. Циклическая обработка пула

После каждого изменения в пуле (завершение BA/TEST, переход в DEV) система циклически проверяет возможность добавления новых задач. Это гарантирует, что свободные места заполняются немедленно.

### 7. Обработка часовых поясов

Все даты форматируются через функцию `formatDateLocal()`, которая использует компоненты даты (год, месяц, день) напрямую, избегая проблем с конвертацией между часовыми поясами. Это гарантирует, что даты записываются точно так, как рассчитываются, без сдвигов из-за часовых поясов.

## Использование

### Запуск расчета

1. Откройте Google Sheets с данными
2. В меню выберите "Workload Tools" → "Рассчитать дедлайны"
3. Убедитесь, что в ячейке Q2 указана дата начала квартала в формате `dd.MM.yyyy`

### Обновление часов

1. При изменении Грейда, Вида объекта или Вида работ автоматически пересчитываются часы
2. Или используйте "Workload Tools" → "Обновить часы" для ручного пересчета всех строк

## Структура данных

### Формат даты

Все даты обрабатываются в формате `dd.MM.yyyy` (например, `01.09.2025`)

### Объект задачи

```javascript
{
  row: number,              // Номер строки в таблице
  analyst: string,          // Имя аналитика
  grade: string,            // Грейд (Senior/Middle/Junior)
  prio: string,             // Приоритет (нормализованный, может изменяться в коде)
  ba: number,               // Часы БА (из таблицы, как есть)
  dev: number,              // Часы разработки (из таблицы, как есть)
  test: number,             // Часы тестирования (из таблицы, как есть)
  baRem: number,            // Остаток часов БА
  devRem: number,           // Остаток часов разработки
  testRem: number,          // Остаток часов тестирования
  stage: string,            // Текущая стадия (WAIT/BA/DEV/TEST_Q/TEST/DONE)
  active: boolean,          // Активна ли в пуле аналитика
  start: Date | null,       // Дата начала
  end: Date | null         // Дата завершения
}
```

## Ограничения и известные особенности

1. **Максимальное количество дней**: расчет ограничен MAX_DAYS (800 дней)
2. **Часы из таблицы**: используются как есть без дополнительных коэффициентов (буферы уже учтены в таблице)
3. **Рабочие дни**: только будние дни, выходные и праздники пропускаются
4. **Параллельность DEV**: максимум 10 DEV задач одновременно (5 программистов × 2 задачи каждый)
5. **Отдельный пайплайн DEV**: DEV команда работает в своем независимом пайплайне с собственной датой и спринтами
5. **Приоритет тестирования**: задачи из тестирования всегда имеют максимальный приоритет
6. **Независимость аналитиков**: каждый аналитик работает в своем темпе с собственной датой

## Контакты и поддержка

При возникновении проблем проверьте:
1. Корректность данных в таблице
2. Формат даты в Q2
3. Наличие всех необходимых листов ("Оценка Q4", "Затраты по грейдам")
4. Корректность заполнения обязательных полей (Аналитик, Грейд, Часы)
